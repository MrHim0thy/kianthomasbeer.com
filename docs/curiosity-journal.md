# Curiosity Journal: content and automatic publishing

## What is ready, and what is not activated

The journal UI, shared validator, catalog builder, publisher, dispatch client, and GitHub workflow are implemented. Four example lessons demonstrate SQL and German; none are represented as Kian's completed learning or real publishing history. Example publishing goals are illustrative and editable. Analytics default to real publications only. Example analytics require an explicit toggle.

No scheduled task, credential, repository variable, commit, push, workflow run, or deployment was created or changed remotely. `JOURNAL_AUTO_PUBLISH` must be set to the string `true` in GitHub repository variables after owner review before the new publishing job will run. There is deliberately no cron in the workflow: it cannot retrieve a private ChatGPT lesson by itself.

## Single source of truth

- Subjects: `content/journal/subjects.json`.
- Lessons: one JSON file per entry in `content/journal/lessons/<id>.json`.
- Shared field validation and TypeScript types: `src/data/journal/validation.mjs` and `validation.d.mts`.
- Generated public catalog: `public/data/journal/catalog.json` (ignored in Git; regenerated by `npm run dev` / `npm run build` pre-hooks).
- Browser loader/filtering: `src/data/journal/journal.ts`.

Add another subject to the subjects array; the UI needs no subject-specific changes. Use a unique lowercase hyphenated ID, name, category, description, active boolean, and color (`amber`, `sage`, `sky`, or `navy`). Optional `goal` contains `targetLessons`, `label`, and `example`. Goals count published notes, not completion or mastery. Remove the example flag only when you deliberately set a real publishing goal. A subject marked inactive remains available as an archived track and filter.

For a lesson, copy an existing example's structure. Required fields: `id`, `subjectId`, ISO `date`, `title`, `summary`, `status` (`published` or `draft`), `example`, `tags`, `source`, `content`. IDs must match filenames and cannot contain paths. Blocks support `paragraph`, `heading`, `list` (items), `code` (language + text), and `exercise`. All rendering is escaped React text. HTML is never interpreted, and SQL snippets never execute. No Markdown parser or third-party editor is required.

Real manually authored notes use `example: false` and `source: {"kind":"manual","label":"Personal learning note"}`. Scheduled notes use `kind: "scheduled-task"` and a truthful source label such as "Daily SQL lesson · automated publication". An automatically published lesson is NOT proof it was read or completed. Keep `example: true` / `source.kind: "example"` on demonstration content. Future-dated published entries are rejected; drafts are excluded from the generated public catalog.

Build validation is strict: malformed JSON, duplicate IDs, unknown subjects, invalid dates, and bad blocks stop the build. The browser also validates its fetched catalog and skips ambiguous/invalid entries with a visible warning. All copies of a duplicate ID are excluded rather than selecting an arbitrary winner. Valid empty catalogs show empty states. The timeline searches full text, supports combined subject/tag/date/content filters, expands native details, and paginates without a fixed entry limit.

Run:

```text
npm run journal:validate
npm run test:journal
npm run dev
npm run build
```

Preview `http://127.0.0.1:5175/#/curiosity-journal` when using the currently running server (otherwise use the port Vite prints). If editing content while the dev server is already running, run `npm run journal:validate` and reload the journal. Updating the UI is automatic from shared data; no arrays in the UI need editing.

## Verified integration limits

Official scheduled-task guidance says web tasks can use their available connected tools, while local project tasks need the computer on and desktop app running. It does NOT prove that an existing lesson-delivery task has repository write access or arbitrary HTTP capability. No matching local automation configuration was found in this environment. The existing task's account, permissions, delivery channel, and tool access were not available for verification here.

References (checked November 5, 2026):
- https://learn.chatgpt.com/docs/automations
- https://developers.openai.com/training/walkthroughs/scheduled-tasks
- https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event
- https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow

An ordinary task that only returns lesson text or emails a notification is not a publisher. Instructions alone cannot grant new tool capabilities. GitHub Pages is static hosting and cannot receive authenticated writes. No API key or token belongs in frontend code, a public JSON file, a task prompt, or a `VITE_` variable.

## Preferred automatic pipeline (after one-time approval)

1. Approve and merge this implementation yourself. The existing Pages deployment workflow and custom domain are unchanged.
2. Confirm your scheduled lesson-producing task can run a trusted publishing tool. A project-scoped desktop task can use the provided Node client. A cloud task needs an authenticated workflow-dispatch tool available to that chat. If the current SQL task cannot use either, move/recreate its lesson-generation prompt in a project-scoped task; a local process cannot automatically read the private output of a different ChatGPT task. Keep the same lesson instructions and continuity material accessible there.
3. Store a fine-grained GitHub token in the publisher's trusted environment, limited to THIS repository with Actions: write, using `JOURNAL_GITHUB_TOKEN`; set `JOURNAL_GITHUB_REPOSITORY=OWNER/REPO`. The caller does not need Contents: write: the workflow uses its own scoped `GITHUB_TOKEN` for the commit. Prefer a short-lived GitHub App installation token if an authenticated app/tool already provides one. Do not put credentials in the task prompt or use a public unauthenticated webhook.
4. If branch protection disallows automation pushing to main, use the already approved repository policy or retain manual publishing. This implementation does not bypass branch protection or remove required reviews. GitHub Pages environment approval rules can also prevent unattended deployment. Do not weaken those controls without a deliberate owner decision.
5. Enable repository variable `JOURNAL_AUTO_PUBLISH=true` after reviewing the publishing scope. This is the one-time activation. No per-lesson approval is built into the workflow.
6. Update the existing task's instructions to return a structured lesson AND call the configured publisher. Test one run, then keep its existing cadence. Keep the computer/app running for a desktop task. No additional OpenAI API calls, paid service, database, or subscription are introduced by this implementation. Standard GitHub-hosted Actions are free for public repositories; private repositories must stay within their existing included allowance.

Task prompt addition (use only AFTER authorizing unattended publishing):

> After producing today's SQL lesson, create one JSON lesson using the repository's content/journal schema. Use subjectId sql, status published, example false, and source kind scheduled-task. Describe it as an automatically published lesson, never as completed practice or mastery. Use the UTC publication date. Choose a stable ID such as sql-YYYY-MM-DD-topic; retries must reuse exactly the same ID and payload. Preserve the original lesson text in escaped structured blocks, without private conversation details, credentials, or unsupported claims. Validate through the provided publisher. In a trusted local project environment, save the JSON in a temporary file outside the content folder, then run node scripts/dispatch-journal-lesson.mjs --file ABSOLUTE_TEMP_PATH --send with credentials supplied through the environment. In a supported cloud environment, use the authenticated publishing tool to dispatch publish-journal.yml on main with lesson_json containing that same JSON string. Do not edit other repository files. If publishing tools are unavailable, report the limitation; do not claim the lesson was published. On a retry, reuse the previous JSON rather than generating different content under the same ID.

Additional subjects use the identical workflow after adding their subject definition. There is no SQL-specific logic in the publisher.

## Dry-run testing and manual fallback

Prepare a real-formatted lesson in a temporary file (not an example marked as real for production), then:

```text
node scripts/dispatch-journal-lesson.mjs --file lesson.json --output dispatch-payload.json
```

Without `--send`, this only validates and optionally writes a local payload. It never sends HTTP requests, commits, or deploys. The actual dispatch request body is `{ "ref": "main", "inputs": { "lesson_json": "<JSON string>" } }` sent with an authenticated POST to `/repos/OWNER/REPO/actions/workflows/publish-journal.yml/dispatches`.

To add a real note manually, create its lesson file, run validation/build, and use your normal reviewed Git workflow. To correct a published note, edit its source file deliberately. The automated importer never overwrites conflicting IDs; identical retries are successful no-ops.

## Workflow mechanics and safety

The workflow reads payload text from `GITHUB_EVENT_PATH`, never interpolates it into shell commands, limits payload size to 50 KB, validates the entire collection, writes only a safe `<id>.json` path, tests, builds, and stages only the lessons directory. It does not execute lesson code. Concurrent publishes use normal optimistic pushes, with up to three attempts. After a rejected push, the job fetches/rebases and reruns tests and the build before retrying. Conflicting edits stop the job; it never force-pushes. No concurrency queue silently replaces pending lesson submissions.

The publish job has Contents: write and Actions: write; all other workflow permissions are empty. Existing Pages permissions/concurrency are unchanged. A successful bot-token push does not trigger the existing deployment's push event, so the publishing workflow explicitly dispatches `deploy.yml`. Deployment is also re-requested on an identical lesson retry so a previous dispatch failure can recover. Branch/environment policies still apply. The workflow must exist on main before dispatch can work.

Local tests cover schema failures, empty catalogs, duplicates, draft exclusion, combined filters, new subjects, safe IDs, idempotency, overwrite rejection, payload limits, and the real workflow event envelope. The network-authenticated workflow and final Pages deployment remain untested until approval and account setup. Generated lesson correctness is not guaranteed by structural validation; the task should keep trustworthy teaching sources and report uncertainty.
